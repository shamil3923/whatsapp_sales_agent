# 🤖 WhatsApp Sales Agent

A WhatsApp sales agent powered by Google Gemini, with real-time currency
conversion, web search, and per-user conversation memory.

## ✨ Features

- **🤖 AI-Powered Sales Agent**: Responses generated by Google Gemini 2.0 Flash via [phidata](https://github.com/phidatahq/phidata)
- **💱 Real-Time Currency Conversion**: Live rates from [exchangerate-api.com](https://www.exchangerate-api.com/), 28 currencies listed by name
- **📱 WhatsApp Integration**: Meta WhatsApp Business Cloud API (v18.0)
- **🔍 Market Research**: DuckDuckGo web search available to the agent as a tool
- **📊 Product Catalog**: 200 synthetic SKUs in SQLite, searched with hybrid BM25 + dense retrieval and exposed to the agent as tools
- **🧠 Conversation Memory**: Per-user profile, interests and message history in SQLite, injected as context on every turn
- **📊 Per-Turn Telemetry**: One JSON line per turn with a per-stage latency breakdown, token counts and estimated cost
- **🔑 Webhook Authentication**: Meta's `hub.verify_token` handshake on `GET /webhook`, and `X-Hub-Signature-256` HMAC verification on `POST /webhook`
- **📈 Analytics Endpoint**: `GET /analytics/users` summarising users, interactions and top interests

## 🚀 Quick Start

### Prerequisites

- Python 3.11 or 3.12 (the versions CI runs against)
- WhatsApp Business Account
- Meta Developer Account
- Google AI API Key
- Ngrok (for local development)

### Installation

1. **Clone the repository**
```bash
git clone https://github.com/shamil3923/whatsapp_sales_agent.git
cd whatsapp_sales_agent
```

2. **Create virtual environment**
```bash
python -m venv .venv
# Windows
.venv\Scripts\activate
# Linux/Mac
source .venv/bin/activate
```

3. **Install dependencies**
```bash
pip install -r config/requirements.txt
```

4. **Configure environment**
```bash
cp config/.env.example config/.env
# Edit config/.env with your credentials
```

5. **Run the application**
```bash
# Start WhatsApp bot
python src/whatsapp_integration.py

# Start web interface (optional)
streamlit run src/sales_agent.py
```

## 🔎 Catalog and retrieval

Product knowledge reaches the agent through retrieval, not the prompt. The
system prompt contains no product data at all, so any product claim the agent
makes can be checked against a catalog row.

```bash
python scripts/generate_catalog.py    # regenerate the 200-SKU catalog (seeded)
python scripts/build_index.py         # load into SQLite and embed
python scripts/build_index.py --skip-embeddings   # lexical only, no model download
```

Retrieval fuses two rankings with reciprocal rank fusion:

| Retriever | Catches | Misses |
|-----------|---------|--------|
| BM25 (lexical) | exact identifiers: `RTX 4080`, `M3 Pro`, `XPS 13` | intent with no shared vocabulary |
| Dense (embeddings) | "something for video editing" | part numbers, which embed near their neighbours |

`RETRIEVAL_MODE` selects `hybrid` (default), `dense` or `bm25`, and
`RETRIEVAL_DENSE_WEIGHT` / `RETRIEVAL_BM25_WEIGHT` set the fusion weights, so
the three can be measured against each other rather than assumed.

Semantic retrieval needs `config/requirements-ml.txt` (torch). Without it the
catalog tools log a warning and serve lexical results, so the agent still
works on a fresh clone.

Agent-facing tools: `search_products(query, k)`, `get_product(sku)`,
`check_stock(sku)`. All return JSON so prices and stock stay exact.

## 📏 Measured results

Retrieval is evaluated over 100 queries written from the customer's side, with
gold sets defined by explicit predicates over the catalog. Intervals are
bootstrap 95% CIs; comparisons use McNemar's exact test on paired outcomes.
Full tables and analysis: [evals/RESULTS.md](evals/RESULTS.md).

| Retrieval mode | hit@3 overall | semantic (n=25) | spec-constrained (n=25) | abstains on out-of-catalog |
|---|---|---|---|---|
| random baseline | 0.165 | 0.160 | 0.120 | 0.000 |
| bm25 | 0.565 | 0.240 | 0.640 | **0.333** |
| dense | 0.788 | **0.680** | 0.600 | 0.000 |
| hybrid (RRF) | 0.824 | 0.480 | **0.920** | 0.000 |
| routed | 0.847 | 0.600 | 0.920 | 0.000 |

What survives a significance test:

- **Hybrid beats dense on spec-constrained queries**, 0.920 vs 0.600, 8–0 on
  discordant pairs, **p = 0.008**.
- **Dense beats bm25 overall**, 25–6, **p = 0.001**.
- **Dense beats hybrid on semantic queries** (0.680 vs 0.480) is *suggestive
  but not significant* at n=25 — 6–1 discordant, **p = 0.125**. The mechanism
  is understood (RRF rewards cross-retriever consensus, and BM25 scores 0.240
  against a 0.160 random baseline there) but the sample cannot establish it.
- **"Routed is the best config" does not hold**: 3–1 over hybrid, p = 0.625.
- An **oracle router** using ground-truth labels changes 13 rankings and
  **zero** hit@3 outcomes, so routing is not limited by classifier accuracy.

Dense retrieval **can** abstain, at a cost that must be chosen: a top-1 cosine
floor reaches 73% abstention on out-of-catalog queries but false-abstains on
25% of real ones. The cheapest useful rule is free — BM25 returning nothing
catches 33% at a 5.9% false-abstain cost.

```bash
python evals/run_retrieval.py      # regenerates the tables above
python evals/run_abstention.py     # regenerates the abstention curves
```

## 💾 Storage

Conversation state lives in SQLite (`data/agent.db` by default) in two tables:

- `users` — phone number, name, preferred currency, interests, interaction count
- `messages` — role, content, message type and metadata, capped at the 50 most
  recent messages per user

Earlier versions stored one JSON file per user under `data/conversations/`.
Import those into SQLite with:

```bash
python scripts/migrate_json_to_sqlite.py            # import
python scripts/migrate_json_to_sqlite.py --dry-run  # report only
```

The script is idempotent: re-running it skips messages that are already present.

## 📊 Telemetry

Every conversation turn appends one JSON line to `data/telemetry/turns.jsonl`.
The fields are:

| Field | Meaning |
|-------|---------|
| `ts` | UTC timestamp when the turn started |
| `turn_id` | Unique id for this turn |
| `phone_hash` | Salted SHA-256 prefix of the sender's number |
| `message_type` | Class assigned by the intent classifier |
| `model` | Model id reported by the agent run, when available |
| `stages_ms` | Milliseconds per stage: `classify`, `retrieve`, `llm`, `tools`, `send` |
| `total_ms` | Wall-clock milliseconds for the whole turn |
| `tokens_in` / `tokens_out` | Token counts reported by the model |
| `cost_usd` | Estimated cost, from token counts × `MODEL_PRICE_*` |
| `ok` / `error` | Whether the turn completed, and the exception type if not |

No example values are given here because this repository does not yet report
measured latency or cost figures — run the agent and read your own
`turns.jsonl`.

Notes on reading these numbers honestly:

- `phone_hash` is a salted SHA-256 prefix. Raw phone numbers are never logged.
- `tools` time is **nested inside** `llm`, not additional to it — tool calls
  happen inside the agent's run loop. It is reported by phidata per tool call
  and is omitted when phidata does not report it.
- `cost_usd` is an *estimate*: token counts reported by the model multiplied by
  the list prices in `MODEL_PRICE_*`. It is not a measured bill.

## 📌 Scope and limitations

This is an evaluated prototype, not a deployed product. Everything below is
stated so the feature list can be taken at face value.

**No production traffic.** The agent has never handled a live customer
conversation. The six sessions under `data/conversations/` are development
fixtures with fictional numbers, and no telemetry line has ever been written.
No usage, adoption or time-saved figure is claimed anywhere in this repository,
and every number that is reported comes from a script here that you can re-run.

**Synthetic catalog.** The 200 SKUs are generated by
`scripts/generate_catalog.py` from a fixed seed. Brands and specs are realistic
and internally consistent, but no SKU corresponds to a real listing and there
is no inventory behind it.

**Scope of the agent.** It answers product questions, checks stock and converts
currency. There is no lead capture or qualification, no cart or checkout, no
order placement, and no escalation path to a human agent.

**English only.** Prompts and canned strings are not localised.

**Measured so far:** retrieval and abstention, in
[evals/RESULTS.md](evals/RESULTS.md). Intent classification, latency and
grounding are not yet measured.

**Webhook signatures** are verified only when `WHATSAPP_APP_SECRET` is set.
While it is unset the endpoint logs a warning on every request and accepts
unsigned POSTs, so set it in any deployment.
